# `knowledge-evals` datasets

Pinned eval inputs for the `evals.retrieval` harness. Lives alongside the package source — the dataset is part of the package's contract, not an unrelated top-level artefact.

## `retrieval_eval.jsonl`

JSONL of `{query, source, expected_content_id}` rows consumed by `uv run eval-retrieval` (default `--eval-set` resolves to `packages/evals/datasets/retrieval_eval.jsonl` from repo root). Schema validated by `evals.retrieval.dataset.load_eval_set` — bad rows fail loudly.

Generated by `notebooks/02_build_retrieval_eval_set.ipynb` (committed alongside the dataset). Source corpus counts at generation kept locally in `ai-findings/2026-05-10_source-corpus-snapshot.md` (not in git).

### Why these counts (Option 1)

`research` had only 7 items in the corpus at generation; `notes` had 49. Padding queries-per-doc on thin sources creates per-doc overfit (esp. for chunker comparisons) and inflates nominal-N while real effective-N stays small. The honest read: **research metrics are advisory** until that corpus grows. See `ai-plannings/2026-05-10_build-retrieval-eval-dataset.md` (local) for the targeting rationale.

### Known v0 gaps

- **No hand-curation.** Queries are filtered LLM output (`gpt-4o-mini`, n-gram-overlap ≤0.3). Phrasing leans LLM-ish; a 30%-curation pass toward natural-user phrasing is queued for the next cadence review.
- **No cross-source negatives.** Plan called for ~21 negatives (queries tagged for the wrong source) to catch cross-source bleed; deferred to v1.
- **Source ordering bias.** `raw_store` items skew recent (server's mtime-ordered SELECT); stratified sampling mitigates but doesn't fully neutralise.

### Cadence review

Refresh per-source slices when:
- A source corpus grows ≥2× since last generation, OR
- A new chunker / embedding model is being compared on a previously thin source, OR
- Quarterly (whichever is sooner).

Baseline results land in `data/eval_results/retrieval_<ts>.json` (gitignored, local-only). Keep them locally chronological — baseline-vs-current trends are easier to spot when prior runs aren't overwritten — and tag dataset version (e.g. via `git rev-parse` of the JSONL commit) when comparing across regenerations.
